# pg-cdc Milestone 5 (Operate) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Each task is done test-first with superpowers:test-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make pg-cdc operable in production: an admin API and `pg-cdc parked` CLI for status and parked events, OpenTelemetry traces, metrics and logs behind the `otel` feature that cost nothing when unconfigured, a chaos harness and `loadgen` that verify §4 with recorded numbers, a multi-arch distroless image, and a README and runbook for operators.

**Architecture:** A process-wide `Status` board collects what the session and lanes know (role, epoch, confirmed LSN, in-flight and parked counts, status-update age, slot retention) through atomics, and `/status` and the metrics gauges read it. Parked mutations go to the lane that owns the key, as messages through weak inbox senders, so the HTTP handler never writes to the store and a held handle never keeps a lane alive; reads page through the session's gated store, and a task without claimed lanes answers 409 with the holder from the leader record. Metrics go through a small facade (one atomic load when nothing is installed); the `otel` feature adds the OTLP gRPC exporters, observable gauges over the `Status` board, and tracing layers, all installed only when an endpoint is configured, and flushed within what remains of the SIGTERM budget. A `loadgen` workspace binary holds the workload writer, a fault-injecting HTTP proxy in front of the emulated SNS and S3 endpoints (the chaos wrapper), the chaos checker, and the load scenarios.

**Tech Stack:** Rust 1.99 (edition 2024), tokio, hyper 1 (admin API, CLI client, fault proxy), serde_json, opentelemetry 0.33.1, opentelemetry_sdk 0.33.1, opentelemetry-otlp 0.33.1 (gRPC over tonic with rustls ring), tracing-opentelemetry 0.34.0, opentelemetry-appender-tracing 0.33.1, opentelemetry-proto 0.33.1 and tonic 0.14.6 (the testkit's OTLP receiver), testcontainers (Postgres 14–18, moto 5.2.4), proptest, cargo-nextest, Docker buildx, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-14-pg-cdc-design.md` (§19 item 5). This plan implements §4 criteria 1–7 (measured), §5 (admin component, `crates/loadgen`), §10.2 and §10.4 (alerts, operator access), §11.1 and §11.3–§11.5 (the bounded parked-queue listing and the sink name, R141, R142), §12.7, §13.1 and §13.3 (runbook), §14.6 (chaos row), §15 (`telemetry` section), §16.1 (`pg-cdc parked`), §16.2 (`/status`, `/parked`, redrive, discard, the standby's 409), §17.1–§17.4, §18.3, §18.5 and §18.6. Read the spec with this plan; the spec wins where they disagree, except where a ruling below says why not.

## Rulings

Each ruling is "decision — why — cost if wrong". Numbering continues from milestone 4.

- **R111. Parked mutations run inside the owning lane; the HTTP handler never writes to the store (carry-over 5).** `Lanes::operator()` returns an `Operator` holding `mpsc::WeakUnboundedSender`s of the lane inboxes. A call upgrades the sender of lane `order_key.lane(lanes)` only for the duration of one `send` of `Inbound::Operate`, drops it, and awaits a `oneshot` reply; a failed upgrade, send or reply is `OperateError::Stopped`. The lane queues the operation and performs it at the top of its next loop turn, between its own sink and store calls, so it never races the lane's delivery, removals or status rewrites (§16.2 "No races with delivery"; M3.3: S3 `set_parked_status` is an unconditional read-modify-write). — Why weak senders: `Lanes::stop` closes the lanes by dropping the inbox senders (R98), and a strong sender held by the admin API would keep a lane alive past the grace, abort it, count an abandoned write and leave the leader record active (R85). — Cost if wrong: none.
- **R112. Redrive and discard semantics.** Both answer `Loading` until the key's partition has loaded, `NotParked` for a key with no stored queue, and `Stopped` once the lane is closing (handover). Redrive applies only to a dead head (`stored.dead`): it calls `set_parked_status(key, head, Retrying)`, clears the key's failure and backoff, drops any pending mark-dead for that head and queues a head read, so the event is redelivered and, if the sink rejects it again, dies again. Discard removes the head only when the stored head is the given id (§16.2) and its event is not still waiting to be appended (`Parking`); the head need not be dead. It calls `remove_parked`, decrements the parked count, drops the head from memory, from the ready queue and from any pending mark-dead or removal, and queues the next head read, so the key's next event goes out next (O2: "delivered or discarded"). Neither settles anything: the event settled when it parked (A1). A store error is returned to the operator and changes nothing in the lane. A discarded event whose transaction was not yet confirmed can be replayed after a crash and is sent again once its queue has drained (as R61). — Cost if wrong: an operator sees a discarded poison event once more after a crash.
- **R113. The `Status` board.** One `status::Status` per process holds the epoch of the current claim, the confirmed LSN, in-flight events and bytes, the lanes' `ParkedGauges`, the transport's `StatusClock`, the slot's retained bytes, the count of published tables without FULL identity, and the active session's `ParkedAccess`. Hot values are atomics written with `Relaxed` stores after each ack change; the rest sit in `std::sync::Mutex`es locked only inside setters and `snapshot`. `run_session` clears everything session-scoped when an attempt ends. — Cost if wrong: two relaxed stores per event.
- **R114. Every parked endpoint answers 409 unless this task holds claimed lanes.** A standby, a task waiting `fence_delay`, a draining task and a fenced task all answer `409` with `{"error": "this task is not the active holder", "role", "holder", "leader_state", "epoch"}`, the last three read from the leader record through the raw state store (`null` when absent, unreadable or slower than `HOLDER_LOOKUP_TIMEOUT`). §16.2's "Standbys refuse them" covers reads too, because only the holder can vouch for its queues. Before the state store is built the endpoints answer `503 {"error": "pg-cdc is starting"}`. The session withdraws its `ParkedAccess` at the start of draining, at a fence and at every exit, before the lanes stop. — Cost if wrong: an operator lists parked events on the active task only.
- **R115. Parked reads page through the session's gated store, and the store bounds the work (supersedes the partition-scan design of the first draft).** `GET /parked` never calls `load_parked_heads`, which on S3 lists every event object of a partition (§11.4). It walks queues in order key id order with `StateStore::list_parked_queues` (R141) from `after` (default: the start), in chunks of `min(limit, PARKED_SCAN_LIMIT - examined)` queues with `length_cap` `PARKED_LENGTH_CAP`; reads each listed head (`read_parked(key, None, 1)`, up to `HEAD_READ_CONCURRENCY` at once) for its status, attempts, first failure and last error; applies `status` to the results in key order; and stops at `limit` matches (default 100, at most 1,000), after `PARKED_SCAN_LIMIT` (1,000) examined queues, or when a chunk comes back shorter than asked. `next` is the key of the last match when it stopped at `limit`, the last examined key when it stopped at the scan limit, and `null` when the listing ended. A queue that drained between listing and reading is skipped. `length` is the queue's length up to `PARKED_LENGTH_CAP`, with `"length_capped": true` when the queue holds at least that many (the exact length of a hot key's queue would need every one of its objects listed). One request therefore costs at most `PARKED_SCAN_LIMIT` per-queue listings of one page each, the key listings that find them, and `PARKED_SCAN_LIMIT` head reads, whatever the backlog. `GET /parked/{key}` reads `limit + 1` events after `after` and returns `limit` with `next` as the last returned id when more exist. — Why: a 10-million-event backlog, typically a few hot keys after an outage, must not turn one request into a scan that outlives `OPERATION_TIMEOUT` and repeats on every retry. — Cost if wrong: an operator sees "1,000 or more" instead of a hot queue's exact length; `pgcdc.parked.events` still gives the total.
- **R116. Admin timeouts (supersedes R96's 10 s connection bound).** `ADMIN_CONNECTION_TIMEOUT` is 60 s, so a parked listing can finish; each parked operation is bounded by `OPERATION_TIMEOUT` (30 s) and answers `504 {"error": "no answer within 30s; the operation may still complete"}` after it, because a lane may be inside a 30 s S3 operation (R57) when the request arrives. The CLI waits `PARKED_TIMEOUT` (40 s). — Cost if wrong: an idle admin connection lingers for a minute.
- **R117. Parked gauges.** `events` is the lanes' shared approximate parked count (R64). `keys` counts keys with a stored queue in lane memory, `dead` counts keys whose head is known dead in the store, and `oldest_ms` is the earliest first-failure time among heads whose time is known (a key this session parked, or a head it has read; after a removal the next head's time is unknown until read). Each lane republishes at most once per `STATS_INTERVAL` after a change, waking for it even when idle. — Cost if wrong: after a restart the oldest age misses queues whose heads have not been read yet; heads are read continuously while a backlog drains.
- **R118. `status_update.age` comes from the transport.** `ReplicationStream::status_clock()` returns a `StatusClock` holding the wall-clock time of the last standby status update the worker wrote and flushed. `/status` and the gauge report it only while streaming. — Cost if wrong: none.
- **R119. Slot retention is polled every 10 s by any task holding a control connection.** `catalog::slot_retained_bytes` reads `pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)` for the slot; a background task per attempt runs it every `SLOT_METRICS_INTERVAL` under `CONTROL_QUERY_TIMEOUT` and clears the value on failure. A standby reports it too, so "slot retained bytes above a threshold" alerts even when no task is active. — Cost if wrong: one cheap query every 10 s.
- **R120. The metrics facade and what each metric means.** `metrics::install` sets a global `Recorder` at most once; `metrics::enabled()` is one atomic load; callsites read `Instant::now()` only when enabled. `pgcdc.events` counts `received` at dispatch, `delivered` on a delivered live event or drained head, `parked` per event appended, and `dead` when a dead event lands in the store or a head is marked dead; `table` and `op` come from the event's `table` and `op` attributes (`unknown` when an attribute was omitted, R68). `pgcdc.commit_to_delivery` is recorded for live deliveries only, from the transaction's commit timestamp; drained events count as delivered without a latency, because their commit time is not stored. `pgcdc.sink.duration` has one point per sink call with `outcome` the worst outcome in the batch (`terminal` over `retryable` over `delivered`). `pgcdc.store.duration` has one point per state or payload store call, leader-record calls included. A `first` takeover counts as `kind=clean` (§17.3 lists only clean and unclean; R89). Gauges are observable callbacks over `Status` and `Health`, so they cost nothing on the hot path; `pgcdc.role` and `pgcdc.leader.epoch` carry the resource attribute `service.instance.id` = the holder id, which is how "no active task, or more than one" is alerted (carry-over 1). — Cost if wrong: a dashboard reads `first` takeovers as clean.
- **R121. Enabling telemetry and the `OTEL_*` variables (§17.1).** Telemetry is enabled when `telemetry.otlp_endpoint` or `OTEL_EXPORTER_OTLP_ENDPOINT` is non-empty; the config value wins when both are set. Only OTLP over gRPC is compiled; `OTEL_EXPORTER_OTLP_PROTOCOL` set to anything other than `grpc` logs a warning and gRPC is used. `https://` endpoints use rustls with ring and the webpki roots. The SDK honors `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES` and `OTEL_METRIC_EXPORT_INTERVAL`; the sampler is `ParentBased(TraceIdRatioBased(telemetry.trace_sample_ratio))`. A build without the `otel` feature logs one warning when telemetry is configured and installs nothing. The exporter stack's own targets (`opentelemetry*`, `tonic`, `h2`, `hyper`, `tower`) are never exported as logs, so an export failure cannot feed itself. — Cost if wrong: an operator with an HTTP-only collector needs a gRPC receiver.
- **R122. Telemetry never blocks and fits the shutdown budget (carry-over 4).** Spans, logs and metrics are handed to the SDK's batch processors and periodic reader, whose queues are bounded and drop when full; no tracing layer does I/O. On exit, `main` shuts the providers down on their own thread while the runtime is still running and waits at most `flush_window(deadline, now)` (`min(1 s, what remains of 2 x drain_timeout + 3 s after the signal)`), then shuts the runtime down and flushes the stdout log buffer within what remains of the same deadline (R107). — Cost if wrong: spans and metrics of the last second are lost when a collector is slow at shutdown.
- **R123. Stdout log lines carry trace and span ids only when telemetry is enabled** and the line is emitted inside a sampled span (§17.4); the JSON line gains `"trace_id"` (32 hex digits) and `"span_id"` (16 hex digits). Without telemetry the formatter is unchanged. — Cost if wrong: none.
- **R124. The `pprof` feature (§17.4) moves to v1.1.** The load work measures CPU time per event and RSS from outside the process and needs no profiler. The spec's §17.4 and §20 are amended in Task 15. — Cost if wrong: a profiling session needs an external profiler such as `samply`.
- **R125. The chaos wrapper is a fault-injecting HTTP proxy in front of the SNS and S3 endpoints, not an adapter compiled into pg-cdc.** `loadgen`'s `FaultProxy` forwards to moto and, by a seeded schedule, delays requests (brownout), answers every request with a server error (outage), answers a share with an error before forwarding, forwards and then answers an error (a write that landed but looks failed), or resets the connection. pg-cdc reaches it through `AWS_ENDPOINT_URL_SNS` and `AWS_ENDPOINT_URL_S3`. Terminal outcomes come from oversize rows, which park dead without a payload store (§7.5), not from crafted SNS responses; dropped connections come from `pg_terminate_backend` on pg-cdc's backends. — Why: no chaos code or configuration ships in the binary, every fault goes through the real AWS SDK error classification and retries, and the same proxy drives the §18.5 outage scenarios. — Cost if wrong: per-message terminal faults at a chosen rate need a `Sink` decorator and a config section later.
- **R126. The chaos checker's definition (§18.3).** The workload is upserts only into `loadgen_items(id int PRIMARY KEY, seq bigint, payload text)` with `REPLICA IDENTITY FULL`, from one connection, so `seq` grows in commit order and each change is identified by its `seq`. The checker passes when (1) every committed `seq` was delivered at least once, is still in the parked store, or was discarded by the harness; (2) for each key, the first delivery of each `seq` comes after a delivery of every smaller committed `seq` of that key, or after the successful discard of it, in causal order; and (3) nothing was delivered that was not written (a transaction whose commit returned an error is "uncertain" and may appear or not). Deliveries are read from a FIFO SQS queue subscribed with raw delivery to a FIFO topic, which keeps each message group (order key) in order. Discards are placed in that same order: before each discard request the harness sends a marker message straight to the FIFO queue with the key's order key id as its message group (the group pg-cdc's SNS sink uses on a FIFO topic), so the marker sits after every message pg-cdc published before the request and before every message published once the discard took effect. The checker walks one observation log (deliveries and markers in queue order) and honors a marker only if its discard succeeded; it never uses an unordered final set for the order rule. A discard whose reply was lost or was a 504 is resolved at the end: it counts as successful when its event is no longer stored and was never delivered. — Cost if wrong: a violating publish still in flight while its key's marker is enqueued can land after the marker and be missed; a systematic ordering defect shows long before that race window. Deletes are not part of the chaos workload; they are covered by milestone 1's tests.
- **R127. Chaos runs outside the gate (carry-over 7).** `mise run chaos-smoke` (a seeded 15 s run plus at most 30 s of settling) runs as its own CI job and in `mise run ci`; `mise run chaos` runs 10 minutes with `CHAOS_SEED` (default: the current Unix time) and is run once in this milestone with its result recorded in `docs/load.md`. Neither is part of `mise run check`. — Cost if wrong: a chaos regression shows in CI, not in the local gate.
- **R128. Load numbers come from moto and the discard sink; real SNS is the pre-production check; criterion 4 passes only from an SNS run.** pg-cdc's ceiling is measured against `discard`; the SNS run offers 6,000 events/s, above criterion 4's 5,000, in both its moto and `--real-aws` modes, and measures moto, whose own `PublishBatch` ceiling is measured with a direct client in the same run so a reader can see which side bounded it. Criterion 4's verdict is `pass` only when an SNS run sustains at least 5,000 delivered events/s over its measured window, keeps up (lag below 16 MiB at the end) and has a p99 upper bound below 1 s. The discard ceiling is context, never the verdict. A moto run whose direct ceiling is below 5,000 messages/s is `unverified (emulator-bound)`, never `pass`, and `docs/load.md`, the summary table and the README record criterion 4 as unmet against SNS until the real-SNS run passes. Criterion 4's "p99 commit-to-acknowledgement" is the 99th percentile of `pgcdc.commit_to_delivery` (commit timestamp to the sink's acknowledgement), read from pg-cdc's own OTLP export into the testkit receiver and estimated as the upper bound of the histogram bucket holding the 99th percentile. The run against a real topic (`loadgen load sns --topic-arn <arn> --real-aws`), the R73 check of `PublishBatch` above 256 KiB and of `MaximumMessageSize`, and the Aurora failover test (§13.3) are the pre-production checklist in the runbook. — Cost if wrong: criterion 4 against real SNS stays unproven until that check runs.
- **R129. ## Review Focus

The five inputs or failure modes the spec implies but its listed tests do not exercise, most likely to bite first. Each is pinned by a test in the owning task.

1. **An operator acts on a key while its lane is mid-flight with it** (the head is in memory waiting for a retry, the same event is still waiting to be appended after a partial park, a mark-dead is pending). Expected: no event is resurrected or sent twice, the next event goes out only after the head is delivered or discarded, and nothing is written for a refused request. Tests: Task 2 `discarding_a_retrying_head_in_memory_drops_it_and_sends_the_next`, `discard_while_the_head_is_still_being_parked_is_refused`, `discard_cancels_a_pending_mark_dead`, and the property `o2_a1_operator_redrives_and_discards_keep_each_key_in_order`.
2. **A handover or fence while an operator call is pending or an `Operator` is held** (an ECS deploy during an incident). Expected: the lanes still stop within the grace and the record is released; the pending call answers 409; a draining task refuses new calls. Tests: Task 2 `a_held_operator_never_delays_a_clean_stop` and `operations_after_the_lanes_stop_report_stopped`; Task 3 `an_active_session_publishes_its_status_and_operator_and_a_standby_publishes_neither` (draining withdraws access).
3. **The OTLP collector is down, slow or blackholed.** Expected: logging and the pipeline never wait on it, and SIGTERM still exits within `2 x drain_timeout + 3 s`. Tests: Task 9 `logging_never_waits_on_a_blackholed_exporter`; Task 10 `sigterm_with_an_unreachable_exporter_exits_within_the_budget`.
4. **Malformed or hostile admin requests** (non-hex ids, an unknown status, `limit=0` or `limit=99999`, an unknown query parameter, a missing `?id`, the wrong method). Expected: 400, 404 or 405 with a JSON error, never a panic or a store call. Tests: Task 4 `malformed_requests_are_rejected_before_any_store_call`; Task 5 `parked_commands_reject_malformed_ids_before_sending`.
5. **Listing a large parked backlog** (thousands of keys, or one hot key holding most of the backlog, after a long outage). Expected: each request does store work bounded by its page, not by the backlog, and returns a cursor; a `status=dead` filter over many retrying keys still returns. ### Task 16: A bounded listing of parked queues in the state store

**Unit:** U1 (runs first in the unit)
**Risk:** normal

**Goal:** Give every state store a cursor-and-limit listing of parked queues whose work does not grow with the backlog (R141), so the admin API's `GET /parked` (Task 4) never scans a partition.

**Files:**
- Modify: `crates/pg-cdc/src/state/mod.rs` (the trait method), `crates/pg-cdc/src/state/memory.rs`, `crates/pg-cdc/src/state/filesystem.rs`, `crates/pg-cdc/src/state/s3.rs`
- Modify: `crates/pg-cdc/src/leader/gate.rs` (`GatedStateStore` forwards the listing through the read gate; its test `Recorder` implements it)
- Modify the test doubles so they compile: `crates/pg-cdc/src/leader/record.rs` (`FlakyLeader`), `crates/pg-cdc/src/supervisor.rs` (`FlakyStore`), `crates/pg-cdc/src/lane/tests/mod.rs` (`TestStore`, forwarding to its inner store like its other reads), `crates/pg-cdc/tests/stream/support.rs` (`UnparkableStore`, `RecordingStore`); each forwards to its inner store, or answers as its sibling read methods do
- Modify: `crates/pg-cdc/tests/support/state_store.rs` (the conformance case), `crates/pg-cdc/tests/state_s3.rs`

**Interfaces:**
- Consumes: `StateStore`, `ParkedHead`, `OrderKeyId` (its `Display` is the fixed-width hex used in object names), `S3StateStore`'s listing helper and permits.
- Produces:

```rust
// crates/pg-cdc/src/state/mod.rs
#[async_trait]
pub trait StateStore: Send + Sync {
    // existing methods, plus:
    async fn list_parked_queues(&self, after: Option<&OrderKeyId>, limit: usize, length_cap: usize) -> Result<Vec<ParkedHead>, StoreError>;
}
```

**Logic:**
- The contract is R141's: ascending order key id order, strictly above `after`, at most `limit` queues, `head` the lowest id, `length` the smaller of the queue's length and `length_cap`, keys without events not listed, `limit` 0 an empty list without a store call.
- S3: one listing of the parked prefix with delimiter `/`, `StartAfter` set to a name that sorts after every object of `after` and before the next key's objects, and `MaxKeys` = `limit` (further pages only while fewer than `limit` keys have been found and the listing is truncated); then, per listed key and up to the store's permits at once, one listing of that key's prefix with `MaxKeys` = `length_cap` (continuing pages only while `length_cap` exceeds one page): the first object is the head and the count is the length. No object is fetched.
- Memory: a range over its ordered map. Filesystem: the parked directory's entries, sorted, filtered and truncated, then each listed key's directory read on the blocking pool as its other reads are.
- `GatedStateStore` runs it under `gate.read`, as it does `read_parked`.

**Tests to write first:**
- `tests/support/state_store.rs` conformance `queues_list_in_key_order_from_a_cursor_with_capped_lengths` (run by every store's existing conformance test): keys K1 < K2 < K3 < K4 spread over at least two partitions, K2 with 25 events and the others with one to three; `list_parked_queues(None, 2, 10)` is `[(K1, its lowest id, its length), (K2, its lowest id, 10)]`; `(Some(K2), 10, 10)` is K3 then K4; `(Some(K4), 10, 10)` is empty; after every event of K3 is removed, K3 is not listed; `limit` 0 is empty; an empty store lists nothing.
- `tests/state_s3.rs` `listing_queues_costs_one_page_per_queue_whatever_the_backlog` (Docker, R137): in partition `0x42`, one key with 2,500 events and four keys with one event each, plus one key in partition `0x43`; with a client whose `ListObjectsV2` and `GetObject` requests are counted (an SDK interceptor through `aws_sdk_s3::config::Intercept`, or a counting forwarder in the test), `list_parked_queues(None, 3, 1000)` returns three queues in key order with the busy key's length 1,000, using at most four `ListObjectsV2` requests and no `GetObject`; a second call with `after` = the third key returns the remaining three queues.
- `leader/gate.rs`: the existing `every_gated_call_reaches_the_inner_value_once_open` and `every_gated_call_is_refused_once_fenced` gain a `list_parked_queues` call, which reaches the inner store once the gate is open and answers `Unavailable` once it is fenced, as `read_parked` does.

**Spec and invariants:** §11.3 (the trait and its conformance suite), §11.4 (S3 listings), §11.5, §16.2 (`GET /parked`: head id, status, length and last error). R115, R141.

**Done when:** the named tests and every existing state, gate, lane, supervisor and stream test pass, `mise run check` is clean, and the change is committed as `feat(state): list parked queues from a cursor with bounded work` ending in the two attribution lines.

**Logic:**

**Logic:**
- `setup` (§13.1 order): creates the `loadgen_items` table of R126 (an `int` primary key `id`, a non-null `bigint` `seq` and a non-null `text` `payload`), sets its replica identity to FULL, creates the publication for that table only, then creates each named logical slot with the `pgoutput` plugin.
- `write` (R126, R138): one connection; a seeded `fastrand::Rng`; for each transaction draw its size from `tx_size`; for each row draw a key with `KeySampler`, take the next `seq` (starting at 1), and run one prepared upsert keyed on `id` that always sets `seq` and, by a bound flag that is true for half of the statements, either replaces the payload or keeps the existing one (R138); the new payload is `row_bytes` of random alphanumerics, or 16 KiB on every `toast_every`-th statement; every `oversize_every`-th transaction adds one row with a 300 KiB payload. Statements of a transaction are pipelined on the client. A successful `COMMIT` appends the transaction's changes to `committed`; any error appends them to `uncertain`, logs it to stderr and reconnects. The `Pacer` sleeps so events per second stay at `rate`. On stop, `last_lsn` is `pg_current_wal_lsn()::text`.
- `KeySampler`: weights `1 / (k + 1)^skew` for `k` in `0..keys`, cumulative, sampled by binary search on a uniform draw; keys are returned as `k + 1`.
- `Pacer::delay(events, now)`: with `rate > 0`, the time at which `sent + events` events are due (`start + (sent + events) / rate` seconds) minus `now`, saturating; it then adds `events` to `sent`. With `rate == 0`, zero.
- `FaultProxy` (R125): a hyper HTTP/1.1 server on `127.0.0.1:0`; each request is buffered, then per the current `Faults` and a seeded RNG: `Outage` answers the error at once; a draw under `reset_rate` drops the connection without answering; a draw under `error_rate` answers the error without forwarding; otherwise it sleeps the brownout latency (if any), forwards over a fresh HTTP/1.1 connection to `upstream` with the same method, path, headers (`Host` rewritten) and body, and returns the upstream reply, except that a draw under `error_after_forward_rate` replaces the reply with the error after the upstream answered. The error is, for S3, `503` with `Content-Type: application/xml` and `<?xml version="1.0" encoding="UTF-8"?><Error><Code>SlowDown</Code><Message>chaos</Message></Error>`, and for SNS `500` with `Content-Type: text/xml` and `<ErrorResponse><Error><Type>Receiver</Type><Code>InternalFailure</Code><Message>chaos</Message></Error></ErrorResponse>`. Counters: every request; forwarded; injected errors; resets; `PUT`s and `DELETE`s whose path contains `/parked/`; and SNS requests whose body contains `Action=Publish` or `PublishBatch`.
- `check` (R126): the expected set is `committed`; `uncertain` changes may or may not appear. A marker counts only when its token is in `discards` (the discard succeeded); markers of failed discards are ignored. `delivered` counts distinct delivered seqs, `duplicates` the extra deliveries and `discarded` the counted markers. `missing` is every committed seq neither delivered, nor in `stored`, nor discarded by a counted marker. `phantoms` is every delivered seq that is neither committed nor uncertain. For order, walk `observed` in order keeping, per key, the set of seqs cleared so far: a delivery clears its seq, and a counted marker clears its seq at the marker's position, never earlier; on the first delivery of seq `s` for key `k`, every committed seq of `k` below `s` must already be cleared, else push `OrderViolation { key: k, seq: s, missing_before: <the smallest such seq> }`. A discard that happens after a later seq was delivered therefore never excuses that delivery. `passed` is all three lists empty.
- `delivery_from_envelope`: `key.id` as the key and `after.seq`, else `before.seq`, as the seq, both from JSON numbers; anything else is `None`. `observed_from_message` reads a `loadgen_discard` marker as `DiscardMarker`, else an envelope as `Delivered`; anything else is `None`.

Start a reader task that receives from the FIFO queue (10 per call, 1 s wait), deletes each message, and appends `observed_from_message(body)` to `observed` in arrival order (FIFO keeps each message group, so each key, in queue order). Every 1 s until `duration`, with `fastrand::Rng::with_seed(seed)`:
  - `choose` draws one action with weights `KillActive` 10, `TermActive` 10, `DropConnections` 10, `SinkOutage` 15, `StoreBrownout` 10, `ErrorBurst` 10, `Nothing` 35. `KillActive` SIGKILLs the instance whose `/status` role is `active` (or `draining`) and restarts it 0.5–2 s later; `TermActive` SIGTERMs it and restarts it once it exits; at most one kill or handover is in progress, so at least one instance always runs. `DropConnections` runs `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE application_name = 'pg-cdc'`. `SinkOutage` sets the SNS proxy to `Outage` for 3–10 s; `StoreBrownout` sets the S3 proxy to `Brownout(200–1500 ms)` for 3–10 s; `ErrorBurst` sets both proxies to `error_rate` 0.2 (SNS) or 0.1 (S3) with `error_after_forward_rate` 0.05 for 5 s; each window then returns to `HEALTHY`.

A 409 or 503 on the list skips the pass (R126).

- Settle: stop the writer; set both proxies to `HEALTHY`; make sure both instances run; until `settle` elapses or every committed seq is delivered or discarded, keep reading and run the operator pass every second.

Mode `discard`: sample RSS every 100 ms; record idle RSS after 5 s; write one transaction of 50,000 rows, wait for it to confirm, then one of 500,000 rows; record each peak.
