# pg-cdc Milestone 4 (Lead) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Each task is done test-first with superpowers:test-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run pg-cdc as a standby that takes over the slot when it frees, holds a lease while active, fences itself when it loses the slot, hands over cleanly on SIGTERM through the leader record, refuses to start against a misconfigured source (§13.2), and reports all of it through `GET /healthz`, `GET /readyz` and `pg-cdc health`, so a start-first deploy can switch the active subscriber of the replication slot without losing a change.

**Architecture:** Every session attempt now runs validation, then standby polling over the control connection, then `START_REPLICATION` (a 55006 loser keeps polling), then takeover through a compare-and-swap of the leader record, all in `run_session`. The lanes only ever see a sink and stores wrapped by a per-session `WriteGate`: the gate stays closed until the leader record is claimed (after `fence_delay` when the previous holder did not release), and fences (cancelling in-flight calls and refusing new ones) when the lease check task loses the slot or the session ends. SIGTERM drains for `drain_timeout`, parks for at most another `drain_timeout`, stops the lanes, and releases the record only when no write was abandoned, all inside a fixed 3 s tail, so the whole handover fits ECS `stopTimeout` of 15 s. A small hyper-based admin listener serves `/healthz` and `/readyz` from a shared `Health` snapshot.

**Tech Stack:** Rust 1.99 (edition 2024), tokio, tokio-postgres (control connection), `pg-cdc-replication` (walsender PID, SQLSTATE 55006), hyper 1 with hyper-util and http-body-util (admin HTTP), aws-sdk-s3 and the filesystem state store (leader record), proptest, cargo-nextest, `pg-cdc-testkit` (Docker Postgres 14–18, moto).

**Spec:** `docs/superpowers/specs/2026-10-14-pg-cdc-design.md` (§19 item 4; implements §5 leader component and runtime footprint, §6.1 control connection, §9.5, §10.6, §12.1–§12.8, §13.2, §13.3, §14.5 L1–L3, §15 `leadership` and `admin`, §16.1 `pg-cdc health`, §16.2 `/healthz` and `/readyz`). ## Rulings

Each ruling is "decision — why — cost if wrong". Numbering continues from milestone 3.

- **R81. Every session attempt runs validation, standby, acquisition and takeover, in that order, over one control connection.** `run_session` opens the control connection, validates (§13.2), polls the slot as a standby (§12.2), sends `START_REPLICATION` when the slot is free, takes over (§12.4) and then streams; the supervisor's reconnect backoff paces attempts after any error, fence or conflict. Validation therefore runs "at process start, in any role" and again after every reconnect, which is how a slot lost mid-run (§13.3) turns the task unhealthy. The role decisions live in small functions over interfaces (`SlotProbe`, `StateStore`, `WriteGate`, tokio time) that are unit-tested with paused time (Tasks 3–6); their composition in the session is covered by Docker tests (Tasks 11–15). — Why: one code path for start, reconnect, fencing and conflict. — Cost if wrong: an attempt after a transient error repeats three catalog queries.
- **R82. Health is a shared snapshot; `/healthz` and `/readyz` read it.** `/healthz` is 200 when sink preflight passed, the store check passed, the latest validation verdict passed, and the role is standby or the lease is valid (§16.2); otherwise 503. Only a validation verdict changes the validated flag: a connection or query error leaves it as it was, because that is a transport fault the reconnect loop owns, not a misconfiguration. `/readyz` is 200 only when healthy, active and delivering, and delivering starts when the leader record is claimed and stops at SIGTERM. A standby is healthy and not ready, so a start-first deploy proceeds and stops the old task, while a misconfigured new task is never healthy and the old task keeps running (§13.2). — Cost if wrong: during a database outage an already-validated standby stays healthy; an active task still turns unhealthy when its lease lapses.
- **R83. One `WriteGate` per session sits between the lanes and every sink, state store and payload store call.** It starts closed (calls wait, reads included, so heads load only after the claim, §12.4 step 4), opens when the leader record is claimed, and fences when the lease task loses the slot or the session ends for any reason. Fencing cancels every gated call in flight at once by dropping its future and refuses every later call (`Outcome::Retryable` for the sink, `StoreError::Unavailable` for the stores). Leader-record calls from the leadership code use the raw store and bypass the gate. A standby has no lanes and a closed gate, so it cannot write (L3), and a task writes only while it holds the slot and the claim (L1). — Cost if wrong: none; the gate only adds an await per call.
- **R84. Fencing bounds the last write by cancelling, not by waiting (carry-overs 2 and 4).** Let `t_ok` be the last successful lease check: the old holder fences no later than `t_ok + lease_timeout`, the slot was still held at `t_ok`, so the new holder acquires after `t_ok` and writes no earlier than acquisition plus `fence_delay`; every write of the old holder issued before the fence therefore has `fence_delay − lease_timeout` (4 s at the defaults, positive by validation) to land before the new holder's first write. At the fence, every gated future is dropped: an S3 or SNS request not fully sent never lands; one already sent lands within the service's own processing time; a filesystem store call already in `spawn_blocking` finishes its few syscalls and fsyncs. Both fit the margin; a write delayed past it is the §12.8 paused-process limit, and each kind of stale write yields duplicates, never a loss: `append_parked` is create-only and writes each key's events in id order (§11.3 item 8), so a late append extends a prefix; `remove_parked` only removes events the old holder delivered; a late `set_parked_status` can bring back a removed event (M3.3), which is redelivered once, or, if it was marked dead, waits for an operator discard; a late sink send is a duplicate the consumer dedupes by id. The cross-task `set_parked_status`/`remove_parked` race of M3.3 is closed by L1: the old holder's last status write lands inside the margin, before the new holder's first removal. The filesystem store keeps releasing its permit when its caller is cancelled (M3.2, MR8); the gate's abandoned-write count (R85), not the permit, decides whether a release is clean. — Cost if wrong: a stale write that lands after the margin gives a consumer a duplicate or an operator a resurrected dead event to discard.
- **R85. The leader record is released only when the session is quiescent.** At SIGTERM the record is swapped to `released` only if the session claimed it, its lease task never fenced, and the gate counted zero abandoned writes (a write call whose future was dropped before it completed, which happens only when a lane is aborted or the gate fences). Otherwise the record stays `active` and the successor waits `fence_delay`. The release is a compare-and-swap on the claim's version, so if another task already claimed, the release conflicts and is only logged; if another task acquired the slot and is still waiting, its claim conflicts, it returns to standby (R93) and its next attempt finds the record released. — Why: after a clean release the successor writes at once, so a write still in flight from this task could land after the successor's first write. — Cost if wrong: a handover with a stuck sink or store costs the successor `fence_delay`.
- **R86. Shutdown has a fixed budget (carry-over 3).** From SIGTERM: stop reading; wait at most `drain_timeout` for in-flight events to settle; then `Lanes::park_all` and wait at most another `drain_timeout`; then a tail of `HANDOVER_TAIL` (3 s) shared by stopping the lanes (at most `LANE_STOP_GRACE`, 1 s, then abort), the release swap and `ReplicationStream::stop`, each bounded by the tail's deadline (a `stop` cut short drops the stream, which closes the socket and frees the slot). The worst case is `2 × drain_timeout + 3 s` = 13 s at the defaults, inside ECS `stopTimeout` of 15 s; operators who raise `drain_timeout` must keep `stopTimeout ≥ 2 × drain_timeout + 3 s` (README). The milestone 3 gaps are accepted because they replay and the bound holds: a lane stuck in a sink call past the park window (M3.11) is aborted at the tail and its abandoned write keeps the record active; keys in a partition that loads after `park_all` (M3.9) and a hot key's long queue parked one object at a time (R75) replay on the next holder. — Cost if wrong: a SIGKILL at `stopTimeout` turns the handover into a crash takeover, which is safe and waits `fence_delay`.
- **R87. The final status update is the one `ReplicationStream::stop` sends, so the release swap comes just before it.** §12.5 lists the final status update (step 3) before the swap (step 4). The transport sends its final status update inside `stop`, together with CopyDone, and the swap must precede closing the connection, because the slot frees when the connection closes. By the time of the swap the lanes have stopped, nothing confirms afterwards, and the swap records exactly the confirmed LSN that `stop` then reports. The spec text is not amended. — Cost if wrong: a crash between the swap and `stop` leaves a released record whose LSN is ahead of the slot's `confirmed_flush_lsn`; the successor starts at once and replays from the slot, so the result is duplicates. The fix would be a `ReplicationStream::send_status` call before the swap.
- **R88. An `active` record always costs `fence_delay`, even when its holder is this process.** §12.4 makes no exception, and a session that ended on an error dropped its lanes with writes possibly in flight. — Cost if wrong: an in-process reconnect after a transient error pauses delivery for `fence_delay` (reading continues); the alternative is to skip the wait when the holder is this process and its last session abandoned no write.
- **R89. An absent leader record is a first takeover.** The task claims epoch 1 at once (`TakeoverKind::First`), because no milestone 4 task can have written without a record. — Cost if wrong: the first deploy of this milestone over a running milestone 3 task, which never wrote a record, skips `fence_delay` once.
- **R90. Definitive slot loss fences at once.** A lease check that finds another walsender, no walsender, or no slot fences immediately; a check that fails or hangs counts as no success, and the task fences when no check has succeeded for `lease_timeout` (§12.3). — Why: never slower than the spec's bound, sometimes faster. — Cost if wrong: none.
- **R91. Lease timing.** The lease starts when `START_REPLICATION` succeeds. Checks run every `POLL_INTERVAL` (2 s) from then on, each bounded by the interval and by the lease deadline; a check returning the task's own walsender PID renews the lease to the moment it returned. Config validation requires `lease_timeout` greater than 2 s (otherwise every lease would lapse between two checks) and `fence_delay` greater than `lease_timeout` (§15). — Cost if wrong: a timing constant.
- **R92. A standby that loses the race keeps polling.** `START_REPLICATION` failing with SQLSTATE `55006` returns the standby to polling at the 2 s cadence, with no reconnect backoff and no health change; any other failure ends the attempt and the supervisor backs off. — Cost if wrong: none.
- **R93. Takeover details.** Leader-record reads and swaps during takeover and release retry store errors with full jitter from 100 ms to 2 s until they succeed or are cancelled, and a retried swap resends the identical record (same `updated_ms`), so R65's equality check turns a swap that landed before its response failed into a success. A claim that conflicts ends the attempt with `SessionError::Takeover(TakeoverError::Conflict)`: the session fences its gate, stops its lanes, stops the stream (releasing the slot) and logs an error, which is the alert until milestone 5's metrics; the supervisor's backoff returns it to standby (§12.4 step 3). An epoch that would overflow `u64` is `TakeoverError::EpochExhausted`, which is fatal. — Cost if wrong: none.
- **R94. Leader-record calls bypass the parking semaphore (carry-over 1).** `S3StateStore::read_leader` and `swap_leader` take no permit from the `state_store.max_concurrency` semaphore, and the filesystem store runs its leader operations in `spawn_blocking` without its permit, so lease, takeover and handover timing never waits behind a parking fan-out. The leadership code makes leader calls one at a time, so they need no bound, and the AWS HTTP client's connection pool is not capped. — Cost if wrong: at most one more concurrent S3 request.
- **R95. The holder id is `<host>-<pid>-<8 random hex digits>`,** where `<host>` is the `HOSTNAME` environment variable when set and non-empty and `pg-cdc` otherwise, generated once per process. — Why: unique across restarts in one container, where the PID repeats. — Cost if wrong: cosmetic.
- **R96. The admin HTTP surface is two endpoints on hyper, and `pg-cdc health` is a small hyper client.** `GET /healthz` and `GET /readyz` answer `200` or `503` with a one-line `text/plain` body; another method on either path is `405` with `Allow: GET`; any other path is `404`. `/status`, the parked endpoints and the `parked` CLI stay in milestone 5. The listener binds `admin.listen` before the sink and store checks, so a starting task answers `503`; failing to bind exits 1. `admin.listen` must be an IP address and port (no host names); port 0 is allowed and the bound address is logged as `admin listening`. `pg-cdc health [--addr <ip:port>]` takes its address from `--addr`, else `PGCDC__ADMIN__LISTEN`, else `127.0.0.1:9187`; an unspecified IP (`0.0.0.0`, `::`) connects to the loopback address of the same family; it exits 0 only on a `200` within 2 s and exits 1 otherwise with one line on stderr. — Cost if wrong: two tasks sharing a network namespace need distinct `admin.listen` ports (README).
- **R97. Validation details (§13.2).** One catalog query gathers `wal_level`, the current database, the slot's plugin, database and `wal_status`, and whether the publication exists; checks run in the spec's order (wal_level, slot exists, plugin is `pgoutput`, database matches, `wal_status` is not `lost`, publication exists) and the first failure is reported. `wal_status` `unreserved` passes and logs an error; `NULL`, `reserved` and `extended` pass silently. A physical slot fails the plugin check. `SessionError::SlotMissing` is replaced by `SessionError::Invalid(Invalid::SlotMissing(slot))`, whose message keeps milestone 1's "replication slot <slot> does not exist". — Cost if wrong: none.
- **R98. Lanes stop gracefully within a bound.** `Lanes::stop(grace)` replaces `Lanes::shutdown`: it aborts the head loader (which holds clones of the lane inboxes), closes the inboxes, waits up to `grace` for every lane to finish its current call and exit, aborts the rest, and reports whether every lane exited on its own. — Cost if wrong: none.
- **R99. `leadership.drain_timeout` replaces `session::DRAIN_TIMEOUT` (supersedes R63's constant).** Both shutdown windows use it. — Cost if wrong: none.
- **R100. Tests use short leadership timers.** The stream harness, the CLI tests and the multi-process tests set `lease_timeout: 4s` and `fence_delay: 4500ms`, and the handover tests set `drain_timeout: 1s`. A 4 s lease leaves a check up to 2 s to answer under a loaded CI machine; the stream harness keeps the default 5 s `drain_timeout` that milestone 3's shutdown tests assume. — Cost if wrong: slower tests or a rare spurious fence.
- **R101. Deferred to milestone 5.** The `pgcdc.role`, `pgcdc.leader.epoch` and `pgcdc.takeovers` metrics, role-change spans and the "no active task, or more than one" alert (§17) are logs in this milestone: role changes at info, takeovers at info with their kind, fences, conflicts and slot loss at error. The §14.6 chaos harness stays in milestone 5; this milestone pins L1–L3 with the named tests below and three multi-process tests. The standby's 409 for parked operations (§16.2) arrives with the admin API. — Cost if wrong: none for correctness.
- **R102. The testkit can start Postgres without logical decoding.** `PostgresOptions` gains `wal_level: WalLevel` (`Logical` by default, or `Replica`), so the `wal_level` validation outcome is tested against a real server. — Cost if wrong: one field.

## Review Focus

The five inputs or failure modes the spec implies but its listed tests do not exercise, most likely to bite first. Each is pinned by a test in the owning task.

1. **The state store is slow or throttled during a takeover or a handover** (a parking backlog holding every S3 permit, `503 SlowDown`, a hung request). Expected: leader calls never queue behind parking; takeover retries until the store answers; a release that cannot reach the store does not stretch shutdown past its budget and leaves the record active. Tests: Task 2 `leader_calls_do_not_wait_behind_parking_traffic` and `leader_calls_bypass_the_permits_parking_holds`, Task 4 `store_errors_during_takeover_are_retried_with_the_same_record`, Task 14 `a_release_that_cannot_reach_the_store_still_exits_within_the_budget`.
2. **The control connection dies while the replication connection keeps streaming** (a backend killed by an operator, a half-open socket). Expected: the task fences within `lease_timeout` of its last good check, closes the replication connection, keeps the record active, and returns to standby. Tests: Task 6 `a_check_that_hangs_still_fences_at_the_deadline`, Task 13 `l1_a_session_whose_control_connection_dies_fences_within_lease_timeout`.
3. **SIGTERM arrives at an awkward moment** (while standby, during the `fence_delay` wait, with a sink call stuck). Expected: exit 0 quickly, the record untouched before the claim, the whole shutdown within `2 × drain_timeout + 3 s`, and whatever was not delivered or parked replays. Tests: Task 5 `shutdown_while_waiting_returns_none_without_starting`, Task 14 `shutdown_before_the_claim_leaves_the_record_untouched` and `a_handover_with_a_stuck_sink_keeps_the_record_active_and_ends_within_the_budget`, Task 15 `a_standby_that_loses_the_race_keeps_polling` (its standby exits 0 on SIGTERM).
4. **`admin.listen` is misconfigured or already taken** (a host name, or two tasks sharing one network namespace during a start-first deploy). Expected: config validation names the field; a taken port exits 1 at once with a clear message instead of running without a health endpoint. Tests: Task 1 `admin_listen_must_be_an_ip_and_port`, Task 9 `run_exits_when_the_admin_address_is_taken`.
5. **The slot is dropped, invalidated or recreated while pg-cdc runs** (§13.3). Expected: streaming stops, the task turns unhealthy and keeps retrying without recreating anything, and resumes once an operator recreates the slot; a `lost` slot blocks, an `unreserved` one only warns. Tests: Task 11 `a_dropped_slot_fails_validation_until_it_is_recreated`, Task 8 `a_lost_slot_fails_validation_and_an_unreserved_slot_only_warns`.

### Task 4: Takeover and release of the leader record

**Unit:** U2
**Risk:** high

**Goal:** Implement §12.4 steps 2–3 and §12.5 step 4 over the `StateStore` leader record: claim it at once when it is absent or released, after `fence_delay` when it is active, with a strictly increasing epoch, and release it with the confirmed LSN.

impl fmt::Display for TakeoverKind; // "first", "clean", "unclean"

#[derive(Debug, Clone, PartialEq, Eq)]

    pub record: LeaderRecord,
    pub version: Version,
    pub kind: TakeoverKind,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, thiserror::Error)]
pub enum TakeoverError {
    #[error("another writer changed the leader record")]
    Conflict,
    #[error("the leader epoch cannot grow past u64::MAX")]
    EpochExhausted,
    #[error("takeover cancelled")]
    Cancelled,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]

pub fn holder_id() -> String;
pub async fn take_over(

    holder: &str,
    confirmed: Lsn,
    fence_delay: Duration,

**Logic:**
- `take_over`: read the record, retrying each `StoreError` after a `Backoff::new(LEADER_RETRY_BASE, LEADER_RETRY_CAP)` delay (warn log with the error), each wait cancellable (cancel returns `Cancelled`).
  - Absent: kind `First`, next epoch 1, expected version `None`.
  - `Released`: kind `Clean`, next epoch `previous.epoch + 1`, expected `Some(version)`.
  - `Active` (whoever the holder, R88): kind `Unclean`; log at warn "the previous holder did not release the slot cleanly; waiting fence_delay before writing" with the previous holder, its epoch and the wait in ms; sleep `fence_delay` (cancellable); next epoch `previous.epoch + 1`, expected `Some(version)`.
  - `previous.epoch + 1` uses `checked_add`; overflow is `EpochExhausted`.
  - Build the record once: `{epoch, holder, state: Active, confirmed_lsn: confirmed, updated_ms: now_ms()}`; swap with the expected version, retrying `StoreError`s with the same backoff and the identical record and version (R93). `Swapped(version)` returns the `Claim`; `Conflict` returns `TakeoverError::Conflict`. The record is never re-read during or after the wait: the compare-and-swap is the only guard.
- `release`: build `{claim.record with state: Released, confirmed_lsn: confirmed, updated_ms: now_ms()}` once and swap it against `claim.version`, retrying `StoreError`s with the same backoff until it answers (the caller bounds the call with its deadline, R86). `Swapped` is `Released`, `Conflict` is `Release::Conflict`. The epoch is unchanged.
- `holder_id` follows R95 (`fastrand::u32(..)` formatted as 8 lowercase hex digits).

**Tests to write first** (paused time; `MemoryStateStore`; a `FlakyLeader` wrapper fails a configured number of `read_leader` and `swap_leader` calls with `StoreError::Unavailable` and records every record passed to `swap_leader`):
